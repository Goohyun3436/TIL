## Overview

- 사내망 서비스 구축 시에 고객 장비에 소프트웨어만 설치하여 배포하는 경우도 있지만, 서버 데스크탑을 통째로 납품하는 경우도 많다.

- <strong>설치된 프로그램을 다른 PC 로 복제해서 사용하는 것을 어떻게 막을 수 있는지</strong>가 궁금헸다.

- 보통 라이선스로 해당 프로그램에 접근 여부를 따지는 걸로 들었는데, 보통 <strong>라이선스 키는 어떻게 동작</strong>하며, <strong>라이선스 키에는 어떤 정보들이 담겨있는지</strong>도 궁금했다.

- 이번 정리는 데스크탑 소프트웨어를 <strong>exe 와 같은 빌드 형태로 납품</strong>할 때 어떤 방식으로 라이선스를 부여할 수 있는지, 그리고 왜 MAC 주소 하나만 보는 것보다 하드웨어 핑거프린트 방식을 적용해야하는지 중심으로 정리한 기록이다.

> <strong>Node-locked license</strong>: 특정 PC 한 대에 묶어서 사용하는 라이선스 방식  
> <strong>Hardware fingerprint</strong>: 여러 하드웨어 정보를 조합해 만든 장치 식별값  
> <strong>Clone protection</strong>: 설치된 프로그램이나 라이선스를 다른 PC 로 복제해서 사용하는 것을 탐지하거나 막는 방식

<br />

## 문제 상황

소프트웨어를 웹서비스처럼 계정 기반으로 제공하는 것이 아니라, 서버 데스크탑이나 산업용 PC 와 함께 <strong>프로그램 자체를 납품</strong>한다고 가정하면, 고객이 그 프로그램 폴더를 그대로 다른 PC 에 복사해서 실행하지 못하게 막아야 할 것 같았다.

<br/>

아래 같은 상황에서는 클론 프로텍션이 필요할 거라고 판단했다.

- 서버 데스크탑 한 대를 통째로 납품하는 경우

- 프로그램은 설치형 또는 exe 형태로 동작하는 경우

- 고객이 백업 또는 복제를 이유로 다른 PC 에 같은 프로그램을 옮겨 실행할 수 있는 경우

- PC 한 대에 대한 라이선스만 허용하고 싶은 경우

<br/>

궁금했던 점은 아래로 정리된다.

1. 라이선스 키는 실제로 어떤 방식으로 동작하는가

2. 라이선스 키 안에는 어떤 정보가 들어가는가

3. 다른 PC 로 복제됐을 때 어떤 기준으로 다른 장비라고 판단할 것인가

<br />

## 라이선스 키는 어떻게 동작하는가

라이선스는 <strong>저작권자/사용자 간의 이용 방법 및 조건 범위를 명시해 둔 사용 허가권</strong>을 의미한다.

라이선스를 검증하는 주체는 크게 두가지로 나뉜다.

- <strong>프로그램 자체가 검증</strong>: 실행 파일 안에 라이선스 검증 로직이 들어 있고, 프로그램 시작 시 현재 장치 정보와 라이선스를 직접 비교하는 방식

- <strong>라이선스 서버가 검증</strong>: 프로그램이 또다른 운영 서버에 라이선스 상태 확인 요청을 하고, 운영 서버가 활성화 여부를 판단하는 방식

서버 데스크탑 납품처럼 <strong>오프라인 또는 폐쇄망 환경</strong>이 많을 수 있는 경우에는, 운영 서버에 라이선스 활성화 여부 확인 요청이 불가능하다. 즉, 운영 서버 검증 방식을 채택할 거라면 인터넷 연결이 항상 가능하다는 전제 조건을 기재하여 납품해야한다.

<br/>

프로그램 자체 검증 흐름은 아래처럼 이해할 수 있다.

1. 공급사가 제품 정보와 장치 정보를 기준으로 <strong>라이선스를 발급</strong>한다.

2. 프로그램은 실행 시 현재 장치의 정보와 라이선스 안의 <strong>정보를 비교</strong>한다.

3. 허용된 제품인지, 만료되지 않았는지, 등록된 PC 와 맞는지 <strong>검증</strong>한다.

4. 조건이 맞으면 실행하고, 아니면 차단한다.

<br />

## 라이선스 키에는 어떤 정보가 담길까

라이선스 키를 다른 PC 에 복제했을 때 사용이 차단되려면 PC 마다 갖고있는 고유한 값이어야 할 것이다. 구글링을 해봤지만 자세히 나와있지는 않았다. 아래는 이렇지 않을까? 하는 추측으로 적어봤다.

- 제품 ID

- MAC 주소

- 고객사 또는 납품 대상 정보

- 만료일 또는 영구 라이선스 여부

- 변조 방지를 위한 암호화

여기서 중요한 것은 <strong>하드웨어 값을 원문 그대로 넣기보다, 해시하거나 서명한 형태로 저장</strong>해야한다는 점이었다. 그래야 라이선스 파일이 밖으로 노출돼도 원본 장치 정보를 그대로 드러내지 않으면서 검증은 가능하게 만들 수 있다.

<br />

## MAC 주소 하나로만 라이선스 키를 구성해도 될까

MAC 주소 하나만으로 라이선스를 묶는 방식은 생각보다 취약하거나 운영이 불편할 수 있었다.

이유는 아래와 같았다.

- 네트워크 어댑터가 바뀌면 MAC 주소도 바뀔 수 있다.

- 유선 NIC, 무선 NIC, 가상 NIC 중 어떤 MAC 을 기준으로 삼을지 애매할 수 있다.

- 운영체제나 드라이버 설정에 따라 MAC randomization 이 개입할 수 있다.

즉, MAC 주소는 "항상 변하지 않는 절대 식별자"라고 보기 어렵다.

그래서 실제 라이선스 시스템에서는 MAC 주소 하나만으로 구성하기보다, <strong>여러 하드웨어 정보를 조합해서 만드는 방식</strong>이 더 일반적이지 않을까 라는 생각을 했다.

<br />

## 하드웨어 핑거프린트(Hardware fingerprint)

찾아보니 하드웨어 핑거프린트 기반 라이선스라는 것이 있었다. 이 방식은 특정 장비의 여러 특성을 조합해 하나의 식별값을 만들고, 그 값을 라이선스와 묶는다.

예를 들어 아래 같은 값들이 있다.

- BIOS 또는 UEFI UUID

- 메인보드 시리얼

- 디스크 시리얼

- CPU 정보

- MAC 주소

<br />

이렇게 하면 장점이 있다.

- NIC 하나가 바뀌어도 전체 장치가 완전히 다른 PC 로 오인될 가능성을 줄일 수 있다.

- 특정 부품이 교체되더라도 허용 범위를 두는 설계를 할 수 있다.

- 단순 복제와 실제 유지보수 상황을 구분하기가 조금 더 쉬워진다.

<br />

## 납품 시 라이선스 부여 흐름

정리한 흐름은 아래와 같았다.

1. 납품 대상 PC의 장치 식별값을 수집한다.

2. 해당 PC 의 하드웨어 핑거프린트와 제품 정보로 라이선스를 생성한다.

3. 생성된 라이선스 파일 또는 라이선스 키를 그 PC 에 저장한다.

4. 프로그램 실행 시 현재 장치 정보와 라이선스 내부 정보를 비교한다. (배포 프로그램 내에서 or 운영 서버에서)

5. 허용 범위 안에서 일치하면 실행하고, 아니면 실행을 막는다.

이 구조라면 프로그램 파일만 다른 PC 로 복사해도 라이선스 검증 단계에서 막을 수 있다.

<br />

## 복제 사용 방지에서 주의할 점

다만 복제 방지는 너무 빡빡하게 만들면 정상 고객도 불편해질 수 있다.

예를 들어 아래 같은 상황이 있다.

- 랜카드 교체

- SSD 교체

- 메인보드 AS

- OS 재설치

- 가상화 환경으로 이전

이런 상황을 불법 복제로 보면 운영이 불편해질 수 있다. 이런 경우는 좀 더 공부 해봐야 할 것 같다.

<br />

## 결론

- 납품 PC 의 하드웨어 정보를 기반으로 라이선스를 생성하면 다른 PC 로 복제했을 때 검증으로 막을 수 있다.

- MAC 주소 하나만 쓰는 방식은 단순하긴 하지만 안정성과 운영 측면에서 안정성이 떨어지므로, 여러 하드웨어 값을 조합한 <strong>하드웨어 핑거프린트</strong> 방식을 채택할 수 있다.

- 라이선스 키나 라이선스 파일은 하드웨어 식별값을 해시, 서명, 암호화한 형태로 저장하여 라이선스 불법 복제를 막을 수 있다.

<br />

## 느낀 점

- 웹서비스처럼 계정 기반 인증은 폐쇄망과 같이 인증 환경이 불가능한 환경이 있을 수 있다.

- 특히 설치형 소프트웨어 납품에서는 프로그램을 다른 PC에 복제할 수 있으므로 "어느 PC 에 설치됐는가" 자체가 중요한 보안 조건이 된다.

- 처음에는 MAC 주소 하나면 라이선스 관리에 충분할 것 같았지만, 실제로는 운영체제 및 하드웨어 변경 가능성 때문에 훨씬 더 신중하게 봐야 한다는 점을 알게 됐다.

- 앞으로 이런 납품 구조를 설계하게 되면, 단순한 키 검증보다 장비 식별, 위변조 방지, 재발급 정책을 함께 봐야겠다.
