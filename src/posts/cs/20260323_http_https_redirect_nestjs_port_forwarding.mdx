## Overview

- SSL과 AES 암호화를 적용하게되면서, HTTP 와 HTTPS 리디렉션 개념을 다시 정리하게 됐다.

- 이번 정리는 HTTP 와 HTTPS 리디렉션의 기본 개념, Nest.js 에서 리디렉션을 적용하는 방법, 그리고 공유기에서 외부 포트포워딩 정책을 어떻게 연결해서 이해해야 하는지를 함께 정리한 기록이다.

<br />

## 문제 상황

B2B 서비스를 개발하다보면 <strong>네트워크에 대한 설계 문제</strong>를 자주 마주하는 것 같다.

B2C 서비스처럼 도메인을 연결하고 표준적인 HTTP, HTTPS 진입 구조를 쓰는 경우도 있지만, B2B 서비스는 IP 주소 그대로 접속하는 경우도 있고, 아예 내부망에서만 접근 가능하도록 막아두는 경우도 있다.

이런 환경에서는 단순히 "프록시 서버에서 HTTP -> HTTPS 리디렉션을 걸면 끝난다"로 마무리가 안된다..
도메인이 없는 환경에서는 아래 항목들을 더 꼼꼼하게 봐야 했다.

- <strong>외부</strong> 80, 443 포트가 실제로 열려 있는지

- 서버와 클라이언트가 같은 업체 같은 사무실이더라도 사용자가 웹에 <strong>WAN 접속을 하는지 LAN 접속을 하는지</strong>

- 서버와 물려있는 공유기 포트포워딩이 어느 내부 장비와 포트로 연결되는지

결국 이 문제는 단순한 백엔드 코드 설정이 아니라, 아래 세 층을 같이 이해해야 풀리는 문제였다.

1. 브라우저가 어떤 프로토콜과 포트로 요청을 보내는지

2. 공유기 또는 라우터가 그 요청을 어느 내부 서버로 포워딩하는지

3. 내부 서버의 Nest.js 가 그 요청을 받아 어떻게 응답하는지

<br />

## HTTP 와 HTTPS 리디렉션 개념

리디렉션은 서버가 "이 요청은 여기서 처리하지 말고 다른 주소로 다시 가라"고 알려주는 응답이다. 브라우저는 이 응답을 받으면 Location 헤더를 보고 새로운 주소로 다시 요청을 보낸다.

보통 HTTP 에서 HTTPS 로 넘길 때는 아래 흐름으로 이해하면 된다.

1. 사용자가 HTTP 주소로 접속한다.

2. 서버는 이 요청을 직접 처리하지 않고 HTTPS 주소를 Location 으로 내려준다.

3. 브라우저가 HTTPS 주소로 다시 요청한다.

4. 이후부터는 TLS 가 적용된 연결에서 응답을 받는다.

실무에서 자주 보는 상태 코드는 아래 정도로 정리할 수 있었다.

- 301 은 영구 이동 의미라서, 브라우저나 검색 엔진이 이 주소 변경을 강하게 기억하는 경우가 많다.

- 302 는 임시 이동 의미라서, 개발 중이거나 정책이 자주 바뀌는 경우에 더 부담이 적다.

- 307 과 308 은 메서드 보존 의미가 더 분명해서, POST 요청을 그대로 유지해야 할 때 더 안전하게 볼 수 있다.

이번에 다시 이해한 핵심은 <strong>"리디렉션은 보안을 만들어주는 기능이 아니라, 더 안전한 주소로 다시 보내는 기능"이라는 점</strong>이었다.

## Nest.js 에서 리디렉션 적용하기

기존에 서비스 중인 서버가 있기 때문에 구조를 최대한 유지하고 개발공수를 줄이기 위해서
Nginx 와 같은 서비스를 추가하기보다는, 기존의 Nest.js 서버를 활용하여 프록시를 해주었다.

방식은 Nest.js 안에서 HTTP 포트와 HTTPS 포트의 역할을 분리하는 구조이다.
HTTP 서버는 리디렉션 전용으로 두고, HTTPS 서버는 실제 API 응답을 처리하도록 나누는 방식이다.

흐름은 아래와 같다.

1. 사용자가 HTTP 주소로 접속한다.

2. Nest.js 의 HTTP 서버가 이 요청을 받는다.

3. HTTP 서버는 응답을 직접 처리하지 않고 HTTPS 80 주소로 리디렉션한다.

4. 브라우저는 다시 HTTPS 443 으로 접속한다.

5. Nest.js 의 HTTPS 서버는 이 요청을 정상적인 API 요청으로 받아 그대로 응답한다.

즉, HTTP 포트는 "넘겨주는 역할", HTTPS 443 포트는 "실제 서비스 역할"을 맡는 구조였다.

예를 들면 아래와 같은 방식으로 정리할 수 있었다.

```javascript
import * as fs from "fs";
import * as http from "http";
import * as https from "https";
import { NestFactory } from "@nestjs/core";
import { AppModule } from "./app.module";

async function bootstrap() {
  const app = await NestFactory.create(AppModule, {
    httpsOptions: {
      key: fs.readFileSync("./cert/server.key"),
      cert: fs.readFileSync("./cert/server.crt"),
    },
  });

  await app.init();

  const expressApp = app.getHttpAdapter().getInstance();

  https
    .createServer(
      {
        key: fs.readFileSync("./cert/server.key"),
        cert: fs.readFileSync("./cert/server.crt"),
      },
      expressApp,
    )
    .listen(443);

  http
    .createServer((req, res) => {
      const host = req.headers.host?.split(":")[0];
      const url = req.url ?? "/";
      res.writeHead(302, {
        Location: `https://${host}:443${url}`,
      });
      res.end();
    })
    .listen(80);
}

bootstrap();
```

이 구조에서는 HTTP 80 으로 들어온 요청은 모두 HTTPS 443 으로 넘기고, 실제 컨트롤러와 API 응답은 443 에서 처리하게 된다.

다만 여기서 중요한 점은, 이것이 프록시 서버처럼 요청을 대신 전달하는 구조는 아니라는 것이다. HTTP 서버는 요청을 백엔드 안으로 프록시하는 것이 아니라, 브라우저에게 "이제 443 으로 다시 접속하라"고 알려주는 리디렉션 응답만 내려준다.

또 하나 주의할 점은, 이 구조도 애초에 <strong>HTTP 요청이 애플리케이션까지 도달해야 동작한다는 점이다. 외부에서 80 으로 들어온 요청이 공유기나 포트포워딩 단계에서 막히면, Nest.js 의 리디렉션 로직은 실행조차 되지 않는다.</strong>

## 공유기에서 외부 포트포워딩 정책

외부 포트포워딩은 외부에서 들어온 특정 포트를 내부 네트워크의 특정 장비와 포트로 보내주는 규칙이다. 예를 들어 아래처럼 이해할 수 있었다.

- 외부 80 포트 -> 내부 서버 3000 포트

- 외부 443 포트 -> 내부 서버 3443 포트

동작은 다음과 같다.

1. 외부에서 HTTP 로 접속한다.

2. 공유기가 외부 80 포트를 내부 Nest.js 서버 포트로 전달한다.

3. Nest.js 가 HTTPS 주소로 리디렉션 응답을 내려준다.

4. 브라우저는 다시 HTTPS 로 접속한다.

5. 이번에는 공유기가 외부 443 포트를 HTTPS 처리 가능한 내부 서버로 보내야 한다.

주의할 점은, HTTPS 만 열어두고 HTTP 포트를 막아두면 사용자가 HTTP 주소로 들어왔을 때는 리디렉션 응답조차 못 받는다. 외부 진입 포트 정책과 서버 응답 정책을 같이 설계했다.

내가 정리한 기준은 아래와 같았다.

- HTTP 접속도 허용해서 HTTPS 로 넘길 생각이면 외부 80 포트가 앱 또는 프록시까지 도달해야 한다.

- 리디렉션 이후 HTTPS 로 실제 서비스할 경로가 있으려면 외부 443 포트도 올바른 내부 서버로 연결되어야 한다.

<br />

## 적용하면서 정리한 흐름

1. 사용자는 프로토콜과 포트를 포함한 주소로 접속한다.

2. 외부 네트워크 장비는 그 요청을 내부 서버로 전달한다.

3. 내부 서버 또는 프록시는 요청이 HTTP 인지 HTTPS 인지 판단한다.

4. HTTP 라면 HTTPS 주소로 리디렉션 응답을 보낸다.

5. 브라우저는 다시 HTTPS 주소로 접속한다.

6. 외부 443 포트 정책과 내부 HTTPS 처리 경로를 따라 응답한다.

<br />

## 느낀 점

- 리디렉션은 단순히 백엔드 응답 코드 설계 문제가 아닌, 실제로는 브라우저, 포트, 포워딩 정책이 같이 맞물려야 동작한다.

- B2B 나 내부망 환경에서는 공인 IP, 사설 IP, 내부 포트 정책을 먼저 확인해야 실제 접속 흐름이 보인다.

- 앞으로 HTTP 와 HTTPS 전환 이슈를 만나면 서버 코드만 보지 않고, 외부 포트가 어디로 들어와서 어느 내부 포트로 전달되는지부터 같이 정리해야 한다.
